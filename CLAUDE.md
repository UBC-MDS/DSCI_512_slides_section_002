# DSCI 512 slides (Section 002)

Lecture slides for DSCI 512 (Algorithms and Data Structures, UBC MDS).
Students see these decks live in class and study from them afterwards, so everything visible on a slide is teaching material.

## How I teach 

My lecture usually open withs a **question, not a definition**. The lecture starts with something concrete the
students can picture, asked as a question, so they get curious and notice a knowledge gap. Then I build the answer **brick by brick, starting from where are**, and only arrive at the formal concept and its name at the end.

- I break every complex idea into the smallest pieces students can follow.
- I teach with **illustrations, concrete examples, analogies and visualizations**, interactive
  when a slider or a step-through makes the idea click. Never introduce a concept without a
  concrete application.
- Each lecture follows **one real-world story** that every code example comes from (lecture 1:
  Uber; lecture 2: Instagram, with the coat check as the analogy for hashing). One story per
  deck, and one analogy per concept.
- If you edit the slide, make the slide text short. Reveal step by step with `::: {.fragment}` / `::: {.incremental}`.
  Put explanations, answers and live-demo cues in `::: {.notes}`.
- Charts must make the key contrast obvious at a glance (e.g. side-by-side panels against a
  shared baseline with a big "2.0×" vs "4.0×" label). Colours match the words on the slide:
  blue `#2a78d6` (linear), orange `#eb6834` (quadratic / growth), grey `#b8b6b0` (baseline);
  16px text on a transparent background.
- **Use emoji sparingly.** Only when one helps understanding or lets students see something at a glance (✅ and ❌ for right and wrong, ⚠️ for a real caveat, 📷 as the items in a stack or queue demo). No decorative emoji in slide titles, bullets, tables or section dividers, and none as topic markers.
- **Bonus slides** are titled `(Bonus Slide) xxx`, on every bonus slide including the bonus section dividers (e.g. `## (Bonus Slide) Best, worst and average case`). Never `Bonus:` or a 🎁 marker.
- Credit AI-generated images in a `::: footer` ("Image generated by …") and cite sources in footers.
- Link out to `website/math.qmd` and `website/python.qmd` (the cheatsheets) instead of repeating
  their content on a slide. From a deck the paths are `../math.html` and `../python.html`.

## How to write

Write like a human, in plain sentences.

- **Never use a dash as punctuation.** No `-`, no `--`, no `—`, no `–` joining clauses or setting
  off an aside. Use a comma, a colon, a full stop or a new bullet instead. Hyphens inside a real
  compound word (`depth-first`, `key-value`, `float64`) are fine.
- This applies everywhere: slide text, speaker notes, code comments, image prompts, commit
  messages, and your replies in chat.

## Code on slides

**Python computes, OJS only draws.** This is the most important code rule.

- All measurements, formulas, curves, counts, ratios, search results and labels are computed in
  Python, so I can check the logic. Pass them over with `ojs_define(name = value)`,
  keyed by the input value (e.g. `readout[n_zoom]`), and define each OJS name exactly once.
- OJS only does inputs, lookups of the precomputed data, layout, colours and `Plot` marks. no
  formulas, no data built in loops.
- Precompute every value a slider can take, keeping the embedded data small (dense grid only
  where the curve bends) and rounding long floats.
- Charts must use the **same** numbers students see printed on the slide.

**Visible vs hidden.** Visible (`echo: true`) is only code students need to analyse, run or
memorise, written exactly as they would write it themselves, with short teaching comments
(`# n iterations`, `# constant time`) so they can count steps. Everything that only supports a
visualization is hidden (`#| echo: false`, or `#| include: false` for pyodide setup), starts
with a comment saying what it prepares and for which slide, and ends with statements, not bare
expressions. Hidden cells share the kernel, so don't overwrite variables students rely on.
Comments must match the code ("repeat 7 times" goes with `repeat=7`).

**Run it in the browser when you can.** Any code students might want to type and run in class
goes in a `{pyodide}` cell, not a static `{.python}` block or a render time `{python}` cell,
as long as it finishes in about a second or two. Use `{python}` only when the code cannot run
in the browser (`psutil`, big files, `pandas` on a large CSV) or is too slow (real timing
demos). Static `{.python}` blocks are for line by line walkthroughs with `code-line-numbers`,
and should be followed by a runnable `{pyodide}` "Try it yourself" slide. Packages beyond the
standard library (e.g. `numpy`) go under `pyodide: packages:` in the deck's front matter. If a
hidden `{python}` cell used a name that a visible cell used to define, move that import into
the hidden cell when you convert the visible one. Keep browser examples small enough not to
run out of memory.

## Classroom tools

**Never use Agora** — it belongs to a previous instructor. This section uses **iClicker**, but you do not need to show the iClicker sign-up link or qr code again after slide 1. 

- **iClicker question format.** Every iClicker question lists its options as `- \(A) ...`, `- \(B) ...` and so on, one option per bullet (the backslash keeps Pandoc from turning `(A)` into an ordered list).
- **Title slide reminder.** The speaker notes on every title slide (the `data-notes` on the title slide) must include this reminder for me, one item per line:
  `[1] iClicker Cloud open<br>[2] Encourage questions: if one student has a question, likely others do too.`
  Separate lines with `<br>`, never `<ul><li>` (the list spacing leaves big gaps in the notes). Any extra title slide notes go after these, also separated by `<br>`.
